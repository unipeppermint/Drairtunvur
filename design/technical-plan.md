# 光路工坊首版技术方案

版本 1.1 · 整理日期 2026 年 10 月 12 日

采用 Swift、UIKit、Core Animation 和独立的 Swift 规则模块，完成可离线游玩的关卡制方块解谜游戏。首个交付为 10 关完整可玩版本，验证规则、操作和恢复能力；正式首版扩展到 3 章 45 关，全部内容随应用提供，按通关进度开放，不接入内购。

配套资料：[产品方案](product-plan.md)、[四页原型图](lightworks-prototype.png)、[原型说明](prototype-guide.md)。

本方案用于后续实现。2026 年 10 月 12 日检查到的工程基线为 Xcode 26.6、UIKit 与 Storyboard 空工程、Swift 5 语言模式、iOS 26.5 部署目标、iPhone 与 iPad 双设备支持。技术文档中的目标配置尚未应用到工程。

**技术选择围绕清晰的棋盘交互和可靠的局面状态展开。**

| 范围 | 首版选择 | 目的 |
| --- | --- | --- |
| 语言 | Swift；实现目标为 Swift 6 严格并发检查 | 明确界面、存档与提示搜索的并发边界 |
| 页面 | UIKit、Auto Layout、代码布局 | 实现地图、对局、结算、图鉴和设置 |
| 导航 | UINavigationController 与轻量 AppCoordinator | 管理页面跳转和恢复入口 |
| 棋盘 | 自定义 BoardView、CALayer、CAShapeLayer、Core Animation | 绘制格子、玻璃方块、连通光路和脉冲 |
| 规则 | 本地 Swift Package LightworksCore，仅使用 Swift 标准库与 Foundation | 同一规则供游戏、预览、关卡校验和提示使用 |
| 关卡 | 随包 JSON，Codable 解码 | 让关卡内容独立于 UI 代码 |
| 存档 | Application Support 中的版本化 JSON、原子替换、备份 | 保存局面、进度、收藏与成绩 |
| 偏好 | UserDefaults | 保存音量、震动、减少动画等简单设置 |
| 章节开放 | 本地关卡进度与前置条件 | 三章无需额外付费，完成前一章后自动开放下一章 |
| 音效与触觉 | AVAudioPlayer、UIFeedbackGenerator，必要时 Core Haptics | 控制音量、响应中断、提供不依赖声音的反馈 |
| 本地化与无障碍 | String Catalog、VoiceOver、Reduce Motion | 首版中英文本地化与基本可访问性 |
| 验证 | Swift Testing、XCTest UI、Instruments | 验证规则、关键流程、进度开放和性能 |

首版第三方运行时依赖为零；全部关卡和图片随应用分发，主线与章节开放不依赖业务服务器或 App Store 交易服务。不接入 StoreKit、购买服务、商品配置、交易监听或付费权限模型。账户系统、广告 SDK、云存档、排行榜、公开关卡编辑器和在线每日任务排在后续版本。

最低系统版本建议定为 iOS 16.0，布局以 iPhone 竖屏为主，同时完成 iPad 自适应。当前工程仍为 iOS 26.5，部署目标及方向配置作为实现阶段的显式配置项处理。Bundle ID 沿用 com.tmuo.Drairtunvur；签名团队和发布配置按用户授权处理。

**页面只负责交互，规则模块决定游戏结果。**

AppCoordinator 管理导航。GameSessionStore 在 MainActor 上持有当前局面和交互阶段；ViewController 绑定状态，BoardView 渲染棋盘。LightworksCore 接收不可变局面与落子动作，返回最终局面及可供动画播放的事件。存档服务使用独立 actor 串行写入；提示在后台执行可取消搜索，结果返回时检查局面版本。

核心模块不导入 UIKit 或图形框架，也不继承应用目标的默认 MainActor 隔离。局面和动作采用可序列化、可比较的值类型，并满足 Sendable。单次棋盘运算只有 64 格，可直接在用户操作路径中计算；耗时搜索才转移到后台。

建议工程边界为 App、Features、Rendering、Services、Resources，以及本地 Packages/LightworksCore。Features 按 City、Game、Result、Collection、Settings 划分；避免引入额外架构框架或通用依赖注入容器。

**规则版本 1 固定以下语义。**

- 棋盘为 8×8；方块固定朝向，首版没有旋转、重力和自动下落。
- 候选区一批三个方块，允许选择任意一个；三个全部用完才补下一批。方块序列由关卡固定。
- 只有完全在棋盘内、且不与已有方块重叠的放置才成立。一次合法放置消耗一步；拖动和无效放置不消耗步数。
- 一个固定边缘入口作为光源。只有入口格被方块占据时，光源才能进入棋盘。上下左右相邻的占用格导光，斜角不导光。
- 灯塔是底层目标，方块可以覆盖它；只有目标格被占据并接入光源时，才能获得本次充能。
- 合法落子形成至少一条满行或满列时，触发一次光脉冲。无论同时完成几条线，每个可达目标至多增加一格能量，且不超过其容量。
- 传光使用消除前的棋盘。随后同时清除全部满行、满列的并集，交叉格只删除一次。
- 已获得的目标能量保留；目标图标也保留。剩余方块不移动。
- 灯塔全部充满即成功，成功判定优先于步数用尽和无处可放。因此最后一步完成目标可以通关。
- 尚未成功时，步数用尽、当前候选全部无法放置，或者固定序列耗尽且没有候选，均进入失败状态。
- 对局与失败状态允许撤销最近一次合法落子；撤销还原占用格、目标能量、候选区、序列游标、步数和结果。成功结算后通过重玩开启新局。

一次落子的固定处理顺序为：校验位置 → 放置并扣步 → 找出满行满列 → 若有消除则计算消除前的可达目标并充能 → 同时清除 → 补充候选 → 先判成功再判失败 → 产生最终局面和事件。

**动画展示计算结果，存档保存已经完成的规则状态。**

拖动悬停时，在局面副本上调用同一个解析器，得到幽灵方块、预计消除线和充能目标。预览不修改真实局面，也不推进候选序列。落子时再次校验当前局面，避免使用过期预览。

事件携带表现所需的消除前、消除后信息，按放置、传光、目标充能、消除的顺序播放。一次落子在逻辑上只提交一次，动画回调不负责加能量、扣步或发奖励。

播放期间暂缓下一次落子。进入后台或中断动画后，界面直接恢复到已提交的最终局面，不重放计分或充能。所有延迟任务绑定局面版本，重开、撤销或切关时取消过期任务。

**关卡文件包含内容、规则版本和可验证解法。**

LevelDefinition 至少包含 id、schemaVersion、contentVersion、rulesVersion、boardSize、initialOccupiedCells、sourceEntry、targets、pieceBatches、moveLimit 和 referenceSolution。Target 包含稳定 id、位置、所需能量和初始能量；Move 包含候选槽位和落子锚点。

GameState 包含棋盘占用、各目标能量、当前候选、下一批游标、已用步数和结果。运行时占用使用简单的 64 格值数据；搜索缓存可将占用压成 UInt64，不把绘制状态放入规则模型。

初始局面不允许已经填满的行列，避免加载时产生隐含消除。内容校验还覆盖坐标越界、目标重复、非法形状、起始占用冲突、步数与候选序列不足等问题。

每次关卡内容更新都重放 referenceSolution，确认每步合法且能在预算内通关。这个校验只证明存在一条通关路径，不代表任意玩家操作都可继续通关，也不代表参考解是最短解。

**提示依据当前局面搜索，不能机械播放预设答案。**

关卡参考解用于教学和内容回归验证。玩家偏离参考解后，从当前棋盘、剩余方块、目标能量和剩余步数重新搜索。缓存键包含所有影响未来结果的状态以及规则、内容版本。

第一版使用有限预算的深度优先搜索、记忆化去重和动作排序，复用正式落子解析器。先尝试约 500 毫秒的后台预算，真机测试后调整；搜索可取消，不能阻塞拖动。

仅在找到完整成功续局时，把第一步作为经过验证的提示。超时表示尚未找到解，不能报告局面无解或承诺某步必胜；可提供明确标注的策略建议，或引导玩家撤销。只有穷尽相关状态空间才能确认无解。

45 个关卡的内容设计要控制分支规模，并在发布前评估常见偏离局面的提示覆盖率；搜索算法不能替代人工难度设计。

**存档保存当前对局与长期进度。**

SaveEnvelope 保存 schemaVersion、递增 revision、当前关卡与内容版本、当前局面、有限长度的撤销快照、章节进度、最好成绩和收藏 id。序列化结果经临时文件写入后原子替换，保留上次有效备份。

每次合法落子、撤销和完成关卡后请求保存；后台切换再补一次保存。独立 actor 按 revision 拒绝旧状态覆盖新状态。界面只在写入成功后把对应 revision 视为已保存；写入失败保留当前内存局面并允许重试。

加载时先校验版本、坐标、游标与能量范围，失败则尝试备份。迁移失败时保留原文件，避免静默覆盖用户进度。关卡内容版本变更时优先恢复对应旧版本；无法匹配时只重开当前关卡，保留已完成章节和收藏。

通关奖励按稳定关卡 id 幂等合并，重复结算不重复发放；最好步数按最小值更新。章节开放根据已完成关卡集合与固定前置条件计算，存档不保存购买权益或商品状态。

**美术按场景层和交互层分别制作。**

现有四屏原型图用于视觉参照。正式素材重新输出纯场景、前景遮挡、灯光遮罩及图鉴缩略图；按钮、文字、棋盘、方块和光路使用原生绘制。

城市效果由 2D 分层素材、透明度变化和少量位移动画实现。场景节点用原生可点击控件覆盖在图层上；关卡完成时点亮对应遮罩。棋盘始终正视，保留清晰格线和可见目标。

CALayer 管理图层内容与动画适合此类表现；实际帧率仍需真机测量。[Apple CALayer 文档](https://developer.apple.com/documentation/quartzcore/calayer)

玻璃方块用渐变、边缘高光和轻量纹理表现，避免为 64 格分别使用实时模糊。只预载当前场景和必要的下一场景资源；按显示尺寸解码背景，防止大图驻留造成内存峰值。

触控使用 UIPanGestureRecognizer，方块预览稍高于手指。提供点选候选再点选锚点的替代操作，并为格子、候选和目标提供可理解的无障碍标签；目标状态同时使用图形、数字和颜色表达。

**章节与收藏仅按通关进度开放。**

将章节前置条件放入本地内容配置，统一由 ProgressService 或现有进度模块计算关卡可玩状态。港湾为初始章节，完成港湾 15 关后开放温室，完成温室 15 关后开放车站。已完成关卡始终可以重玩；应用重启、离线和存档迁移后保持相同结果。

地图、继续游戏入口和图鉴共同读取进度状态。锁定文案只说明尚未完成的前置条件；提示、撤销和收藏不依赖付费权限。

实现中不创建 PurchaseService、StoreKit 测试文件、商品 id、交易监听、恢复购买按钮或付费墙。如果开发中已有对应实现，应移除相关引用，并让章节路由直接依赖进度模块。既有开发存档中的无关付费字段在迁移时忽略，保留关卡成绩和收藏。

**验收覆盖规则边界和真实用户路径。**

规则测试必须覆盖：非法放置不扣步；斜角不连通；断路不充能；未消行不充能；多行只触发一次脉冲；行列交叉只清一次；充能先于清除；目标容量封顶；最后一步成功优先；补牌后再判无处可放；撤销完整恢复；预览与正式落子结果一致；45 关参考解全部重放通过。

存档测试覆盖原子替换失败、备份恢复、版本迁移和过期写入。进度测试覆盖第 15 关和第 30 关完成后分别开放下一章、重启恢复、重复结算和离线继续。关键 UI 流程覆盖首次教学、连续拖放、通关、重玩、后台恢复、图鉴解锁及大小屏布局，并确认全部 45 关仅凭通关即可访问、所有页面均无购买入口。

性能目标为拖动时稳定接近 60 fps、单次规则及预览运算在低端支持设备上低于 5 毫秒、无搜索导致的主线程卡顿。这些是验收预算，不是已测得结果。使用 Instruments 的 Time Profiler、动画卡顿分析和内存工具，在小屏 iPhone、常规 iPhone 及 iPad 上验证。

**按三个里程碑交付。**

| 里程碑 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| M1 核心可玩 | 规则模块、棋盘拖放、传光预览、10 关、撤销与存档 | 规则测试通过；参考解可重放；后台恢复不重复结算；用户能理解传光策略 |
| M2 完整体验 | 四个主要页面、分层美术、音效、45 关、中英文与基础无障碍 | 主线可完整通关；布局和真机性能达到目标；提示覆盖率经过评估 |
| M3 发布准备 | 全章节离线验证、进度恢复、隐私与商店信息、审核操作路径 | 三章无需额外付费即可通关；关键流程回归通过；全部商店展示与实际功能一致 |

每日模式现使用 DailyChallenge 按本地日期稳定轮换已验证关卡，DailyProgress 独立记录每日局面、撤销历史和最佳步数。旧存档通过可选 daily 字段兼容；保留最近七个局面和全部完成记录。开始后保留题目快照，跨日完成归属于开始日期，主线存档不被覆盖。底部导航展示城市、每日和图鉴。首个编码任务从 LightworksCore 和 BoardView 开始，用一关同时验证连接、充能、消除、撤销和恢复，再扩展页面。
